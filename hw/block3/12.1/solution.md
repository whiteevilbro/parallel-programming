Переведём описание алгоритмов в псевдокод

### Первый:

```java
class FirstBarrier {
    Lock lock = new TATASLock();
    long counter = 0;
    final long goal;
    
    public FirstBarrier(long n) {goal = n;}
    
    public wait() {
        lock.lock();
        counter++;
        lock.unlock();
        while (counter < n) {}
    }
}
```

### Второй:
Его приходится немного модифицировать относительно формулировки в книжке, 
потому что в книжке:
- не указано, что делает 0-й поток, помимо выставления флага
- не указано, что поток по выходу меняет какие-либо флаги

Таким образом, в формулировке из книги 0-й поток моментально покидает барьер, 
и в момент, когда все потоки дошли до барьера, выйти из него могут лишь последний и предпоследний

Модифицированный псевдокод:
```java
class SecondBarrier {
    final int n;
    short b[n];
    
    public wait() {
        long id = Thread.currentThread().threadId();

        if (id == n - 1) {
            while (b[id - 1] != 1) {}
            b[id] = 2; // здесь
            return;
        }
        if (id == 0) {
            b[0] = 1;
        } else {
            while (b[id - 1] < 1) {}
            b[id] = 1;
        }
        while (b[id + 1] != 2) {}
        b[id] = 2;
    }
}
```

### Сравнение:
#### Большая нагрузка:
Первый барьер:  
Пусть большое (N - 1) количество потоков уже зашли в барьер и находятся в ожидании одного последнего.
У всех из них есть своя кэшированная копия counter. 
Приходит последний поток N, загружает значение счётчика (так как оно изменялось другими потоками) в кэш и записывает в свой кэш новое значение счетчика. 
Вместе с этим инвалидируются все кэшированные копии счётчика у всех оставшихся потоков.
При следующей попытке чтения на каждом из этих потоков происходит cache-miss и в кэш загружаются новые данные.
По условию наша система основана на шине, и в этот момент шина будет заполнена, что вызовет задержки, пропорциональные числу потоков.
Фактически, случится invalidation storm, который забьет нам шину.

**Замечание:** то же самое будет происходить при каждом увеличении счетчика. 
Результирующие количество cache-miss: O(n^2) (при каждом обновлении по количеству ждущих потоков). 

Второй барьер:
Разобьем работу барьера на две фазы: до строки, помеченной комментарием, и после.
В каждой фазе все потоки крутятся на своих, попарно непересекающихся ячейках памяти. 
При выходе одного потока из барьера происходит запись в одну ячейку, на которой крутится один поток, 
поэтому обмен кэшами хоть и происходит, но он относительно дешевый. 
Притом каждый поток пишет в чужую ячейку, лишь увидев подходящее значение в своей ячейке, 
то есть после получения обновленного кэша. 
Таким образом шина не имеет "одновременных" перемещений кэшей

**Замечание:** это верно лишь в случае, когда каждый флаг из `b[]` попадает в отдельную кэш-линию (нет false-sharing).
Если это не так, то может происходить ситуация, аналогичная первому барьеру.
Результирующее количество cache-miss: 2n-1 ~ O(n)

#### Малая нагрузка:
При достаточно малой нагрузке и достаточно большой пропускной способности шины разрешение invalidation-storm может произойти быстрее, 
чем несколько разделенных во времени обменов кэшей. 
В такой экзотической ситуации первый барьер может показывать лучшую производительность.

#### Nota Bene
Также стоит отметить, что первый барьер использует константное количество памяти, а второй - линейное.
В случае, когда число потоков превышает количество кэш-линий, условие на "хорошую" работу второго барьера невозможно выполнить,
и в пределе мы получаем invalidation-storm после каждой записи, коих больше чем в первом барьере.
